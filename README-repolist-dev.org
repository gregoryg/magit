How to work on, test, and run Gregory's fork of Magit's repository list.
Direction and decisions are in [[file:PLANNING.org][PLANNING.org]]; status is in
[[file:TASKS.org][TASKS.org]].  Magit's own [[file:../README.org][README.org]] is untouched.

* Where these notes live

=PLANNING.org=, =TASKS.org=, this file, and the superseded =problems.org=
live on the orphan =notes= branch, checked out as a worktree at =.notes/=.
The main worktree lists =.notes/= in =.git/info/exclude=, so the notes never
enter a topic branch.  Commit them from =.notes/=, for example from the Magit
status buffer of any file there.

All worktrees share =.git/info/exclude=, so it must not list the notes' own
file names, or =git add= in =.notes/= silently skips them.

The worktree was created on 2026-11-21 with:

#+begin_src bash
git worktree add --orphan -b notes .notes
echo '.notes/' >> .git/info/exclude
#+end_src

A clone of this repository receives the branch as =origin/notes=.  To read
the notes there, run =git worktree add .notes notes= and exclude =.notes/=.
The update script pushes =notes= to the fork with the other branches, so
these notes are public.

** One-time setup

#+begin_src bash
git config rerere.enabled true
#+end_src

** Start a topic

#+begin_src bash
git fetch upstream
git switch -c repolist/local-variable-p upstream/main
#+end_src

In Magit: =b c= in the status buffer, start point =upstream/main=, then the
name.  Either way, Git records =upstream/main= as the branch's upstream
(Magit's "Merge:" line), while =remote.pushDefault= sends =P p= to =origin=.
Under =push.default=simple=, plain Git does not resolve =@{push}= for this
split, so prefer Magit's =P p= or name the remote and branch explicitly.

A stacked topic starts from the topic it depends on instead:

#+begin_src bash
git switch -c repolist/async-fetch repolist/group-headers
#+end_src

** Commit style

Match Magit's history: subject =function-name: Summary in sentence case=, no
trailing period, body wrapped near 70 columns explaining why.  See
=git log --oneline -- lisp/magit-repos.el= for examples.

- A fix for a regression cites the commit that caused it as a footnote, as in
  =eb8c592f=: =[1: 58a46982]= in the text, and below it
  =1: <date> <full hash>= followed by the indented subject.
- Regression tests go in a separate, following commit titled
  =test: Prevent fixed <function> regression=, as in =d08eca92=.
- Commits carrying a =Co-Authored-By: Claude= trailer contain generated code;
  rewrite those before proposing them upstream (see "Proposing a topic
  upstream").

** Update the integration branch

Run on perihelion after any topic changes, and to follow upstream.  It
moves =gjg= forward and never rewrites it: it merges new upstream commits
and any topic commits that =gjg= lacks, then pushes everything to GitHub.
A topic already merged and unchanged is a no-op, so the script is safe to
run at any time.

It refuses to run with uncommitted tracked changes.  It stops at the first
conflict, which =rerere= may already know how to resolve; resolve it,
commit the merge, and run the script again to continue.  It also stops if
GitHub's =gjg= has commits that the local one lacks, or if a push would not
be a fast-forward, which means a branch was rewritten.

#+begin_src bash :results verbatim
  #!/usr/bin/env bash
  cd "$(git rev-parse --path-format=absolute --git-common-dir)/.."
  set -euo pipefail
  topics=(repolist/local-variable-p
          repolist/group-headers
          repolist/marks
          repolist/async-fetch
          repolist/buffer-naming
          repolist/mark-group
          repolist/act-at-point
          fix/toplevel-tramp-worktree)
  if ! git diff --quiet || ! git diff --cached --quiet; then
    echo "Uncommitted tracked changes; aborting." >&2
    exit 1
  fi
  git fetch upstream
  git fetch origin
  git switch main
  git merge --ff-only upstream/main
  git switch gjg
  git merge --ff-only origin/gjg
  git merge --no-edit upstream/main
  for t in "${topics[@]}"; do
    git rev-parse --verify --quiet "refs/heads/$t" >/dev/null ||
      { echo "skip $t (no such branch)"; continue; }
    git merge --no-ff --no-edit "$t"
  done
  git log --oneline --first-parent -10 gjg
  git push origin main gjg notes "${topics[@]}"
  echo "Pushed.  Update each clone (see 'Running the fork')."
#+end_src
** Follow upstream

The update script merges =upstream/main= into =gjg=; nothing else is
needed.  Topics stay on the base they started from and are not rebased:
they are published, and a pull request is a hand rewrite on a =pr/<slug>=
branch from current upstream anyway (see "Proposing a topic upstream").

To bring a change from a lower topic into a topic stacked on it, merge
the lower topic into the stacked one instead of rebasing:

#+begin_src bash
git switch repolist/async-fetch
git merge repolist/group-headers
#+end_src

* Testing on perihelion

=make= finds dependencies under =ELPA_DIR= or as sibling directories.
Perihelion has no Emacs package directory, and Emacs 32 already provides
=compat=, =seq=, and =transient= 0.13.9.  The rest must be cloned next to this
repository:

#+begin_src bash
cd ~/projects/emacs
git clone https://github.com/tarsius/cond-let.git
git clone https://github.com/tarsius/llama.git
git clone https://github.com/magit/with-editor.git
#+end_src

Then, from the repository root:

#+begin_src bash
make lisp   # byte-compile, autoloads, check-declare
make test   # full ERT suite
#+end_src

=make test= always runs the whole suite.  For a focused run, call Emacs
directly with an ERT selector; this one runs tests whose names match
"repolist".  =load-prefer-newer= keeps a stale =lisp/*.elc= from shadowing
an edited source file:

#+begin_src bash
emacs -Q --batch --eval '(setq load-prefer-newer t)' \
  -L lisp -L ../cond-let -L ../llama -L ../with-editor/lisp \
  -l test/magit-tests.el --eval '(ert-run-tests-batch-and-exit "repolist")'
#+end_src

=make lisp= also compiles =test/magit-tests.elc=, which upstream's
=.gitignore= does not cover; this clone lists =test/*.elc= in
=.git/info/exclude=.

Remove stray =.elc= files from =lisp/= before switching to a branch with
different sources; =make clean= does this.

* Running the fork on the EXWM host

The EXWM host clones =gjg= from GitHub.  The clone is only for running the
fork: never edit or commit there.  Until 2026-11-24 it cloned from
perihelion instead; "Switch an existing clone to GitHub" below moves such a
clone over.

1. Clone the integration branch, refuse merges on pull, and build it with
   the host's own Emacs:
   #+begin_src bash
   git clone -b gjg git@github.com:gregoryg/magit.git ~/projects/emacs/magit
   cd ~/projects/emacs/magit
   git config pull.ff only
   make lisp
   #+end_src
   Do not copy =.elc= files from perihelion: Emacs 32 compiled them.
   =make= finds =cond-let=, =llama=, =transient=, and =with-editor= in
   =~/.emacs.d/elpa=, where MELPA installed them; set =ELPA_DIR= if they
   live elsewhere.
2. Add the clone to the =use-package magit= form:
   #+begin_src emacs-lisp
   (use-package magit
     :load-path "~/projects/emacs/magit/lisp"
     ...)
   #+end_src
   Keep MELPA's =magit= installed: Forge and other packages depend on it,
   and it brings in Magit's dependencies.  =:load-path= puts the clone
   first, so it shadows MELPA's =magit= and =magit-section=.  MELPA's
   autoloads name files rather than paths, so they load the clone's code.
   Only a command that the fork newly autoloads would also need
   =(load "magit-autoloads" nil t)= in =:init=.
3. Restart Emacs.  =M-: (locate-library "magit-repos")= should name the
   clone, and =M-x magit-version= should describe =gjg=, for example
   =v4.7.2-10-gd68433c1=.
4. After each run of the update script on perihelion, pull, rebuild, and
   restart Emacs.  In Magit, =F u= pulls; then run =make lisp=.
   #+begin_src bash
   cd ~/projects/emacs/magit
   git pull && make lisp
   #+end_src
   With =pull.ff only=, a pull either fast-forwards or refuses.  A refusal
   means a branch was rewritten somewhere: find out why before doing
   anything else, and never answer it with =reset --hard=.

** Switch an existing clone to GitHub

For a clone made from perihelion.  Point =origin= at GitHub, drop the
remote-tracking branches that only perihelion had, and refuse merges on
pull:

#+begin_src bash
cd ~/projects/emacs/magit
git remote set-url origin git@github.com:gregoryg/magit.git
git fetch --prune origin
git config pull.ff only
git status
#+end_src

=git status= should report =gjg= up to date with =origin/gjg=.  If it is
behind, =git pull= fast-forwards it.  If the two have diverged, stop and
compare them first.

** Quick trial without rebuilding

For a one-file change, load the edited source into the running Emacs over
TRAMP; it redefines only that file's functions:

#+begin_example
M-x load-file RET /ssh:perihelion:projects/emacs/magit/lisp/magit-repos.el RET
#+end_example

Restart Emacs to return to the installed version.

* Proposing a topic upstream (2027)

Upstream's issue trackers stay locked until early 2027, and
=.github/CONTRIBUTING.md= rejects all LLM-generated code.  It does allow an
LLM to investigate an issue, provided that is disclosed upfront and the
findings are described in the contributor's own words.  So a proposal
starts as a GitHub Discussion (features) or an issue (bugs, once trackers
reopen), and a pull request carries code Gregory rewrote himself, even when
a careful rewrite turns =(message "Hello, World")= into
=(message "Hello, World")=.

1. Branch from the topic's base, so that the two versions stay comparable:
   #+begin_src bash
   git switch -c pr/group-headers 7a05d472
   #+end_src
   =7a05d472= is the base of the 2026 topics.  For a topic rebased since,
   use =$(git merge-base upstream/main repolist/<slug>)=.
2. Rewrite each commit by hand, using the topic only as a reference.  While
   both branches share a base, =git diff repolist/<slug> pr/<slug>= shows
   exactly where the two versions differ.  These commits carry no
   =Co-Authored-By= trailer.
3. Move the branch onto current upstream, then build and test again:
   #+begin_src bash
   git fetch upstream
   git rebase upstream/main
   make lisp && make test
   #+end_src
   After the rebase, compare the two series with
   =git range-diff 7a05d472..repolist/<slug> upstream/main..pr/<slug>=.
4. Push =pr/<slug>= to =origin=, and open the pull request against =main= of
   =magit/magit=.
5. Write the description yourself; the policy rules out generated text.
   Cover:
   - the purpose, linking the Discussion or issue;
   - how to reproduce the problem, and how the fix was verified;
   - upfront, that an LLM (Claude) helped find the cause and drafted the
     original fix, which you then rewrote; and
   - your view that good code deserves credit, whatever its source.

The maintainer may also want an entry in the current =docs/CHANGELOG.*=.
Entries cite commits, so add one when asked.
